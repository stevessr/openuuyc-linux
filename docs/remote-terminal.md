# 远端终端（开发版）

## Linux 被控端

在「被控设置」单独允许终端后，当前已授权主控可创建运行于被控用户身份的 PTY Shell；默认关闭，不提升权限，不开放局域网监听端口。账号、会话句柄和控制连接共同隔离终端。撤销授权沿用既有 `end_login` 清理，结束对应远端 Shell。允许远程新建 Shell 与允许访问本机已有终端是两个独立授权。

已有 UU `kind=8` / `BINARY_DATA_CHANNEL` / `TERM v1` 路径继续保留。OpenUUYC 的已连接桌面使用 `OPENUUYC_TERMINAL_V1` 独立可靠通道承载相同 TERM 帧，避免为打开终端抢占当前桌面连接；该扩展不会假称为官方 UU 已支持的功能。拒绝或撤销可选终端通道不得取消桌面连接的父取消令牌。终端通道不接受通用 protobuf 控制 RPC。

## 客户端入口

- 桌面串流设置 → 高级设置 → 远端终端。
- 安卓设备详情 → 终端：无现成连接时建立专用纯数据终端连接（不协商音视频）；已有桌面中也可从「终端」按钮使用当前连接。
- PICO 沉浸菜单 → 应用 → 远端终端 → 选择设备。输入弹出原生键盘；另提供 Ctrl+C、Tab、方向键和 Esc。

打开界面不立即执行命令，需显式「打开 Shell」。命令需确认发送。UI 关闭会请求结束 Shell；网络断开时不能保证最后一个关闭帧送达，服务端仍遵循既有断线/空闲回收策略。无远端创建确认则不允许输入。

桌面显示使用 vt100 解析；安卓/PICO 是固定 80×24 的有界单色 VT 子集，支持 UTF-8、常见光标移动和擦除，不是完整彩色终端/所有全屏 TUI 的兼容承诺。OSC 不操作剪贴板或打开链接。输出/命令不写日志、配置或诊断包。输入队列与输出缓存有界。

## 后续加固

- 发送端将短时 SCTP 背压视作等待，最多 2 秒；断线/持续拥塞仅关闭可选终端通道，并明确最后输入未经确认。
- 桌面端提供 80×24、100×30、120×36 尺寸请求；协议没有独立 Resize ACK，界面不将请求称为远端确认。
- 安卓输出按有界批次合并到 UI；每次 Shell 切换使旧输出票据失效，防止延迟回调吞掉新输出或覆盖新状态。空闲/未确认终端和过大的输入不会发送。
- 后续验证：4 项 Rust 控制端测试和安卓 241 项 JVM 测试、Lint 通过；新增补丁未完成跨设备验证，PICO 当前仍未连接。

## Codex CLI 语音与 Linux 音频输入

仅终端连接没有 WebRTC 音频轨道；Codex 语音需要一条协商了麦克风的桌面串流，并将远端 Codex 置于键盘焦点。语音按钮现在先等待 Android 录音授权、远端策略确认及麦克风打开，再发送 F8；失败、取消、等待和发送状态分别展示。按钮不会将按键发送成功冒充为识别成功，识别结果由 Codex 自己显示。

Linux 虚拟输入依赖 `pactl`、`pacat` 和 PulseAudio 或 PipeWire-Pulse 的 null-sink/remap-source 支持。仅在用户授权的麦克风策略打开后创建临时源，接收解码后的 48 kHz 双声道浮点 PCM，不读取 Linux 物理麦克风，不播放到物理扬声器。会话关闭释放临时进程与模块。

- 默认不更改系统输入设备，主机的音频默认设备设置仍可显式选择麦克风路由。
- 对明确需要自动输入切换的本机，可使用 `OPENUUYC_REMOTE_MIC_DEFAULT=1 OpenUUYC gui`。授权麦克风打开时临时选择远端源，静音/断开后恢复之前的默认输入；用户中途另选输入时，不覆盖用户的选择。此选项不授予麦克风权限，也不自动录音。
- 现有应用若锁定了旧的录音设备，需要结束并重新开始 Codex 录音；先让虚拟源就绪再发 F8 可以避免初次选择旧源。
- 端到端延迟不是单个队列参数：原生 NetEq 的目标上限收紧为 60 ms，外层丢弃排队超过 80 ms 的旧 RTP 包；Android 后续改为音游 8 包 / 音画同步 40 包，避免一味缩小到 4 包引发过多补偿；音游模式主要取消与视频同组同步等待。包时长和设备输出仍会影响实际延迟，网络抖动大时可能增加丢包补偿。


### 音游音频模式

PICO 默认启用音游模式，可在窗口串流“高级设置 → 音游音频”，或沉浸式屏幕画质圆环的“音频”二级菜单中改回音画同步。选择持久保存，重连生效。音游模式仅在本地接收 SDP 将音轨设为 streamless，不改远端传输、轨道 ID、SSRC、ICE 或视频映射，避免音频与视频分组同步增加等待；可能出现声音先于画面，不适合以嘴型同步为目标的观看场景。

Linux 桌面 monitor 请求最多 30 ms 的采集缓冲，过载时丢弃旧片段，发送队列只保留最近 20 ms。10 ms 分包请求沿用原实现，不保证所有官方主机都会接受。PICO 请求 48 kHz 输出与低延迟播放，不强改系统 PipeWire 量子或全局调度。

诊断 `jbAvg`/`jbTarget` 为连接累计统计；`jbNow`/`jbTargetNow` 为本次与上次采样间隔的统计，第一次或计数重置显示 n/a。它们不包含整条采集、网络、音频设备及声学链路，不能称作按键到耳朵的延迟。音游验收还需实际外部计时或声画录制；蓝牙耳机应单独排除。

### Linux 音频 RT 调度与帧周期队列

主机“连接设置 → 画面与声音 → 低延迟”默认开启并请求 RT，开关重连生效；当前进程的开关可覆盖启动环境。可用 `OPENUUYC_AUDIO_RT=0 target/debug/OpenUUYC gui` 显式关闭，`=1` 显式开启。此开关本身不授予任何远程权限。

仅专用桌面音频采集/麦克风工作线程请求 `SCHED_RR` 优先级 10，不改变 GUI、共享 Tokio 工作线程、整个进程或系统 PipeWire 调度。线程退出恢复原调度；权限不足保持普通调度并在主机设置显示原因，不自动 sudo、改 limits 或安装能力。

RT 队列按当前活动串流最高 FPS 更新预算，多屏共用一路声音。60 FPS 为 16.67 ms、90 FPS 为 11.11 ms；音频处理粒度下限为 10 ms，因此 120/165 FPS 使用 10 ms，不虚报为 8.33/6.06 ms。软件队列保留能放入预算的完整音频块：30 FPS 最多 3 块、60 FPS 及以上 1 块；过期捕获与发送背压也使用该预算。没有视频信息时先按 60 FPS，更新周期 250 ms。底层声卡、服务器采集缓冲、编码与网络仍各有延迟，不等于整条链路只有一个画面周期。


### 短 Opus 管线实验（替代上述旧 10ms 软件块下限）

发送端采集块调整为 120 个 48kHz 采样，即 2.5ms；分包配置以采样数保存，不再用整数毫秒造成舍入。按 RFC 7587 用 `ptime:3` 请求 2.5ms Opus 包，兼容 5/10/20ms 等原有分包；PICO 的音游模式才发送该短包请求，音画同步模式保留 10ms 请求。实际选择仍取决于对端，不能把 SDP 请求当作远端已经按 2.5ms 发包。

Linux/Windows loopback 和主控麦克风的短块时钟一起调整，RTP 每短包递增 120，不使用 144（3ms），避免持续漂移。主机短块队列按帧周期预算裁剪：60/90/120/165/240 FPS 分别最多 7/5/4/3/2 个 2.5ms 块（向上量化，避免批量回调被截碎；时间戳过期检查仍限制旧数据）；低延迟关闭时仍保留最多 20ms，不因块缩小意外变为 5ms。Linux RT 采集轮询缩短至 1ms。Native 接收验证允许短 Opus 包，但 NetEq 每次取样及 PICO Java WebRTC 播放接口仍按 10ms 工作；这次突破的是采集和编码分包下限，不是声学端到端 2.5ms。

短块实机验证还修复了 libpulse 事件处理瓶颈：单轮事件循环不足以处理每片数据随后产生的 deferred 工作，普通 5ms 轮询曾只能交付约 208 块/秒；现在每次采集前有界清空就绪事件（最多 8 轮），实测恢复 400 块/秒。过期片段只裁掉过期前缀，保留有效尾部；RTP 时钟在真实缺口处按捕获时间推进，不把丢掉的时间压缩进连续时间戳。本机服务端实际返回片段 2048 字节（48kHz float32 双声道约 5.33ms），所以内部 2.5ms 切块不等于服务端 I/O 也只有 2.5ms。

### 原生 AAudio 自适应通路（OpenUUYC 扩展 v1）

音游模式现在优先尝试 `OPENUUYC_AUDIO_V1`。这是一条现有加密 WebRTC 连接内的独立、不重传、无序数据通道，不是官方 UU 的新接口。主机必须正面声明版本、48kHz 双声道、120 采样块及支持的两种编码；官方主机或不支持扩展的版本继续走 RTP。

- 原生捕获队列/发送工作独立于 RTP 编码，不等待暖备 RTP 的编码或背压。两路使用同一已授权捕获源，不另外录制麦克风。每块与发送前都复查会话许可、代次和时间戳；队列及通道背压有界，过期直接丢弃。
- 原生 Opus 使用 `OPUS_APPLICATION_RESTRICTED_LOWDELAY`；稳定窗口且观测 RTT 不超过 12ms 时尝试 16-bit PCM。丢包、欠载和抖动触发 Opus/缓冲调整，带切换冷却与过渡安定期，不每帧反复改编码。PCM 48kHz 双声道负载为 1.536Mbit/s，另有传输开销及保留的 RTP 流；主机为此预留额外带宽。
- AAudio 优先请求独占低延迟，失败尝试共享低延迟；格式/设备能力不满足则回退。回调只搬运有界无锁环形队列，不做 JNI、网络、解码或内存分配。解码在独立音频优先级工作线程上完成。
- 先确认 AAudio 回调真实运行、收到当前 epoch 的合法数据且缓冲就绪，再静音仍持续接收的 RTP 并启用原生输出。通路超时、设备错误或持续欠载退回 RTP；15 秒后可重新探测。切换不承诺声学完全无缝，暖备会占用额外 CPU/带宽。
- 新通路不经过 Java WebRTC 的 10ms 播放缓冲或 NetEq 取样 API；仍受设备 burst、系统输出缓冲、解码和网络约束。原生模式诊断显示实际 burst/buffer、包数、已消耗采样、欠载及丢弃统计；不能把这些计数当作测得的按键到耳朵延迟。

构建通过 CMake 拉取 SHA-256 固定的 Opus 1.6.1 源码；离线可传 `-DOPENUUYC_OPUS_SOURCE=/path/to/opus-1.6.1`。完整 BSD-style 许可位于 APK 的 `assets/licenses/opus.txt`。C++ 环形队列/协议可用 host 编译器与 ASan/UBSan 检查，Android `native-audio` instrumentation 仅生成静音、不联网、不采集物理麦克风。真实音游、持续运行、丢包及切换验收仍须在头显连接后完成。
